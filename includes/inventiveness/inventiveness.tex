\section{Introduction \& Background}

\subsection{Background}

Blockchains are economic data structures that provide an append-only transaction log that is secure against an attacker.
That append-only log is extended via ``blocks''.
Blocks cannot be created arbitrarily and the producers of blocks are typically rewarded.
A block is a cryptographic data structure that includes a specific collection of transactions.
Each block points back to one or more parent blocks.
Typically, a newly created block will use the ``tip'' of the blockchain as its parent block(s).
Once a new block has been created, it is broadcast over the network, and nodes will validate the block and extend their local copy of the blockchain.
Thus, each newly created block provides new transactions, extends the chain, and allows future blocks to point back to it, facilitating an ongoing cycle of: create, broadcast, validate, append, create, etc.

When a new block is created, broadcast, validated, and accepted as an extension of the blockchain, that block provides a ``confirmation'' to all prior blocks, and to all transactions both in prior blocks and in the new block.
Once a transaction has received a sufficient number of confirmations (and the corresponding block is still part of the canonical chain), the transaction is considered ``confirmed''.
The number of ``confirmations'' that a block or transaction has is 1 plus the number of blocks that build on top of that block (or, for a transaction, the block that the transaction was contained in).
A new block builds on top of all prior blocks that it is cryptographically dependent on.

Each block has a property called ``weight'' that corresponds to the amount of ``work'' that was required to create the block.
For blockchains using a consensus system based on \emph{Proof of Work}, ``weight'' and ``work'' are both measured in \emph{hashes} --- particularly, the average number of hashes that the network (in aggregate) needed to calculate in order to find a valid block.
The weight of multiple blocks is simply the sum of their individual weights --- thus the weight of the full chain is the sum of all blocks between its initial block (the genesis block) and the ``best'' known block.
This is how a consensus algorithm \emph{chooses} the best block: it is the valid block with the greatest total weight of all blocks between it and the genesis block.
Block producers are incentivized to build on the best block because they receive a smaller reward (often 0) if they build on other blocks.

A function known as \emph{the fork rule} encapsulates the specific calculations involved in how a particular consensus algorithm chooses the best block.
Particularly, the fork rule determines which of two possible chain histories (complete sequences of blocks) is the canonical one --- the one that block producers should build on and extend.

The \emph{security} of a blockchain (or a network of chains) is measured by the amount of resources that an attacker would need in order to effect a doublespend.

A doublespend is when an attacker makes a valid transaction, which then seems to be confirmed as a permanent part of the ledger, and then that attacker publishes previously private blocks that cause a chain \emph{reorganization}.
The effect of this is that the previously valid transaction is now invalid.
A doublespend is conceptually similar to a credit card charge-back that is made after a consumer has received the goods.

The \emph{speed} of a blockchain is inversely proportional to the duration that a user has to wait before a transaction is considered ``confirmed''.
This duration is measured in ``confirmations'' --- e.g., it is common for users to consider a Bitcoin transaction confirmed after 6 confirmations (which takes approximately 60 minutes).
After this number of confirmations has occurred, it is taken that the chances of an attack succeeding are so low that the possibility can be dismissed --- thus a transaction is considered secure after this point.

\subsection{Block Headers and State}

Blockchains typically specify that blocks have a \emph{header} --- a small data structure (usually between $\sim 100$ and $\sim 1000$ bytes large) that includes crucial cryptographic metadata.
That metadata typically includes (but is not limited to): the hash of the parent block(s), a cryptographic commitment (often a merkle root or equivalent) to both/either the transactions included in the block and/or the current \emph{state} of the blockchain, network information such as the \emph{difficulty}, the timestamp of the block's creation, a \emph{nonce}, and protocol version information.
Certain classes of consensus protocols (e.g., those based on \emph{Proof of Stake}) may require additional data to be included in the header.

Since a block header is distinct from the transactions in the corresponding block, a \emph{headers-only} chain can be constructed.
A \emph{headers-only} version of a blockchain is typically sufficient to verify both the \emph{order} of blocks (and thus transactions) and the \emph{chain-weight} of the chain; however, the corresponding chain cannot be \emph{fully} validated because the validity of all constituent transactions is not established (that requires downloading and evaluating those transactions).

\emph{Headers-only} chains are still secure, though, since the work required to produce them is practically equivalent to the work required to produce the full blockchain.
Thus, headers-only chains are as secure against an attacker as the full chain \emph{in most circumstances} (note: the exceptions are not relevant here).

We can use headers-only chains via their commitment to both/either the transactions included in the block and/or the current state of the blockchain.

The state of a blockchain is protocol dependent --- a rough general description is: all of the up-to-date data required to evaluate whether new transactions are valid and, if so, the results of those transactions.
For example: the state of the Bitcoin blockchain is all of the current \emph{unspent transaction outputs} set; and the state of the Ethereum blockchain is all current account balances, all smart contract code, and the databases of all smart contracts.

It is possible to exclude an explicit commitment to the exact transactions in a block (since the resulting state root will not match if an incorrect list of transactions is evaluated), but this is costly.
Typically, all but the earliest generation of blockchains specify headers that include commitments to both transactions and state.

These cryptographic commitments use systems chosen for their ability to produce succinct proofs.
For example: it is efficient to prove that a bitcoin block contains a specific transaction, or, on an Ethereum-based blockchain, to prove the balance of a specific account.
The method of constructing a headers-only chain (or chain-segment) and verifying that a transaction was included in one of the corresponding blocks is known as \emph{Simple Payment Verification} (SPV) and was initially detailed in the Bitcoin whitepaper (2008).

Although PoR and UT do not technically require succinct proofs, the overall throughput of the method is highly sensitive to the size of these proofs (with smaller proofs corresponding to higher throughput).

The exact set of things that can be proven in this way is protocol dependent.

\section{Proof of Reflection}

\emph{Proof of Reflection} (PoR) is the foundational method of UT.

\subsection{Key Concepts}

\subsubsection{Projection / Imaging}

Blockchain transactions can include many different types of content.
Particularly, we are interested in the case where transactions include the headers of blocks from other blockchains.
This situation can be useful for users of a blockchain network.
For example: it is possible to write an Ethereum smart contract which accepts the headers of Bitcoin blocks and constructs a headers-only version of the Bitcoin chain.
Such a smart contract can (provided all relevant headers have been provided) then be used to prove that a transaction has occurred on the Bitcoin network.
Since there is no established term for this concept (a headers-only version of one chain recorded and evaluated by a second chain), we call this a \emph{projection} of the first chain in the second chain.
Alternatively: the second chain \emph{images} the first chain.
\emph{Image} in this case is a verb, and the result of a second chain imaging a first chain is the projection of the first chain in the second.

\subsubsection{Reflection}

When both a first chain images a second chain and the second chain images the first, we say that each chain contains a \emph{reflection} of the other.
That is: the first chain can use its projection of the second chain to prove which blocks of the first chain have been imaged by the second chain.
When two chains image one another in this way, we say that the chains reflect one another.
When we say that a block of one blockchain was reflected (or imaged) by a block of another blockchain, we mean that the header of that block was included as part of the block of another blockchain in a way that is able to be proven.

The word \emph{reflection} is used because a projection of a projection is a reflection.

A \emph{proof of reflection} is a multi-stage proof that: a specific ancestor block ($L_a$) of a first block ($L_i$) of a first blockchain (\cL) was reflected by a specific block ($R_j$) of a second blockchain (\cR), and that the block of the second blockchain ($R_j$) was in turn reflected by the first block of the first blockchain ($L_i$).
Thus, a PoR is comprised of these three parts:
\begin{enumerate}
  \item A proof that $L_a$ is an ancestor of $L_i$; and
  \item A proof that $R_j$ reflected $L_a$; and
  \item A proof that $L_i$ reflected $R_j$.
\end{enumerate}

Note that full nodes of the \cL chain already know the first and last part (i.e., they already have all the data required to verify whether they are true).
Thus, the crucial ``missing'' part of the PoR is the middle proof: that $R_j$ reflected $L_a$.

We typically use \cL and \cR to denote the ``local'' and ``reflecting'' chains, and $L_n$ to identify the $n^{th}$ block in the \cL chain (and similarly for $R_n$ in the \cR chain).

Note: the proper noun ``Proof of Reflection'' refers to the system where proofs of reflection (PoRs) are used, in combination with the conversion of work, to increase the security of a blockchain.

\subsection{Method --- Using PoRs}

One of the key ideas behind PoR is that the weights of blocks are summable.
In isolation, this fact is already used by traditional PoW blockchains (such as Bitcoin) to calculate chain-weight.
Chain-weight is the total amount of work that has contributed to a complete sequence of blocks from the genesis block to any other specific block.
The chain-weight of a blockchain is the chain-weight between the genesis block and the best block.

A key \emph{insight} here, is that the weight of blocks in \emph{different} blockchains can, in certain contexts, contribute to an individual blockchain's security through a process of recording PoRs and \emph{converting work}.

Typically, the chain-weights of two different blockchains are not able to be directly compared as they are measured in different \emph{dimensions}.
In the universal and generic case, it is not possible to convert between different dimensions; rather, we need a specific goal and context in order to convert.\footnote{
  Attribution: \href{https://criticalfallibilism.com}{Critical Fallibilism}; e.g., see \href{https://criticalfallibilism.com/multi-factor-decision-making-math/}{Multi-Factor Decision Making Math}.
}
% A dimension is a range of all possible values that are qualitatively unique.
For example: the dimension of \emph{duration} (of time) is qualitatively different to the dimension of \emph{distance}.
We know that duration and distance are different dimensions both because they measure different things, and because there is no way to generically convert between the two.
Similarly, the weight of blocks from one blockchain may be measured in hashes of one type (e.g., SHA256) and the weight of blocks of another blockchain may be measured in hashes of a different type (e.g., ETHash).

Only by introducing certain contexts can we convert between different dimensions --- including different weights of different blockchains.
For example: in the context of some object with an unchanging \emph{velocity}, we do have a way to convert between distance and duration --- the velocity acts as a \emph{constant of conversion}.
If the object has velocity $s$, and moves some distance $d$, then it must have done so in $d/s$ units of time.
Just as the context of the above example enables conversion between distance and duration, PoR requires that we choose a suitable context to enable the conversion of work.

There are two known methods of conversions and each is dependent on a different context.
These methods and contexts are detailed primarily in the whitepaper sections ``Comparing Incomparable Proofs of Work'' and ``Conversion Contexts''.

The conversion of work is novel and a key component PoR.

Algorithms for conversion are detailed in \autoref{sec:patent-conversion-algs}.

Assuming that work can be converted, how do blockchains actually integrate the work of other, different, blockchains?

The key insight is that a block can use a proof of reflection of an ancestor block, combined with the conversion of work, to increase the chain-weight of the chain-segment that it builds on.
That is: when the fork rule is comparing chain-weights of two competing chain-segments, it counts the work contributed by each local block, and the work contributed by all reflecting blocks (which is equivalent to the reflecting blocks' individual weights, summed).

Also, there are some principles that the fork rule's implementation of PoR should adhere to:
\begin{itemize}
  \item contributed work should not be double-counted (i.e., each reflecting block can contribute its weight exactly once only); and
  \item when an \cR block reflects multiple \cL blocks that form a continuous chain-segment, the work contributed by that \cR block should be attributed to the most recent \cL block in that chain-segment; and
  % \item one of the following (these points are equivalent): \begin{itemize}
  %   \item where more than one block is reflected and those blocks form a continuous chain-segment, contributed work should be attributed to the reflected block(s) that were created most recently (i.e., are at the tip of that/those chain-segment(s)); and
  %   \item where a reflecting block reflects multiple blocks that form a continuous chain-segment, the work that the reflecting block contributes should be attributed to the tip of that chain-segment; and
  %   \item when an \cR block reflects multiple \cL blocks that form a continuous chain-segment, the work contributed by that \cR block should be attributed to the most recent \cL block in that chain-segment; and
  % \end{itemize}
  \item a block, $R_j$, in a reflecting chain (\cR) that does not reflect any local blocks (\cL blocks) eventually contributes its weight to the same \cL blocks that were reflected by the most recent ancestor of $R_j$ that reflected \cL blocks; and
  \item a chain, when considering contributed weight, should only consider reflections of blocks in its own history --- if a later block builds on two chain-tips\footnote{
    This is possible in some DAG-based blockchain data structures, e.g., \citeInclusiveFull.
  } that were reflected by the same \cR block, then care should be taken to avoid double-counting the work contributed by that \cR block.
\end{itemize}

This method works because, for an attacker to successfully perform a doublespend, they are required to produce a chain-segment with a weight greater than the individual weights of all relevant \cL and \cR blocks that have contributed work to the chain-segment that the attacker wishes to undo.

If chain \cL accounts for reflected work in this way, but chain \cR does not, then it may be possible for an attacker to first attack chain \cR so as to enable a cheaper attack on \cL.
However, this is only possible: if chain \cR does not use PoR; or if there is a large asymmetry between the work contributed by \cL and \cR, such that the work that \cL would contribute is negligible for chain \cR.
If both chains \cL and \cR use PoR (a situation called ``mutual reflection''), then attacking either chain is as difficult as attacking both.

\section{Simplexes}

Simplexes are collections of chains that all mutually reflect one another.
Blockchains that are part of a simplex are called \emph{simplex-chains}.
The simplest possible simplex has 2 simplex-chains.

Simplex-chains only need to consider proofs of reflection concerning their own history because blocks of all simplex-chains include the headers of blocks of all other simplex-chains.

The capacity of each simplex-chain can be separated into two parts: one part for recording other simplex-chains' headers and relevant PoRs, and the other part for recording all other transactions.
Meaningful transactions from users are counted in the latter part.

The number of simplex-chains in a simplex is constrained by the size of the first part, and the number of meaningful transactions per second is constrained by the second part.

We can calculate the optimal ratio of these two parts in order to maximize the number of meaningful transactions that a simplex can process.
The result is approximately that half the capacity of each chain should be dedicated to each part; i.e., $\sim\half$ to reflections and PoRs, and $\sim\half$ to other transactions.

Such a simplex, given reasonable parameters,\footnote{
  The relevant parameters are: block size, block frequency, and block header size.
  We particularly consider: $k$ (bytes/s), a generalization of block size which is the product of block size and block frequency; $B_f$ ($\text{s}^{-1}$), the block frequency; and $B_h$ (bytes), the size of each block header.
} can host hundreds or thousands of simplex-chains.
Additionally, simplex-chains can be incrementally created and added to the simplex as the network's capacity requirements increase.

\section{Blockchain ``Speed'': Confirmation Time}

The amount of time that a user of a chain must wait in order for their transaction to be ``confirmed'' is network dependent.
Some networks take longer than others.
This is because, for an attacker that controls $q$ proportion of the network's security,\footnote{
  By convention a PoW blockchain's security is analyzed in terms of an attacker with $0 < q < 0.5$ proportion of the network's hash-rate, such that the ``honest'' block producers have $p$ proportion, and $p + q = 1$.
} the chance that a doublespend succeeds depends on the number of confirmations that a user waits --- the more confirmations, the lower the chance of a successful doublespend; the larger $q$ is, the higher the chance of a successful doublespend.
For transactions of lower value, a user can afford to wait for fewer confirmations than a more valuable transaction.

When two blockchains use mutual PoR, the confirmation rate (\Cprime) of each chain \emph{increases}: a confirmation is received for each local block and each reflecting block.
In essence: in a simplex with 2 simplex-chains, each simplex-chain has $2\times$ the confirmation rate that it would have if it were not using PoR; a simplex with 3 simplex-chains has $3\times$ the confirmation rate; and so on.

What does this mean for users?
Consider a simplex-chain which is part of a simplex with $N$ simplex-chains.
That simplex-chain has $N\times$ the confirmation rate that it would if it were standalone (i.e., not part of a simplex).
Consequently, to achieve an equivalent level of security, users of that simplex-chain need to wait $N^{-1}\times$ as long as they would need to wait if the simplex-chain were standalone.
Equivalently: confirmation waiting time has decreased by a factor of $N^{-1}$, i.e., confirmations happen $N\times$ more often.

Practically speaking, this means that large simplexes confirm transactions almost instantly (after the first confirmation, which is when a transaction is included in a block).

\section{Miner Resonance (Lower variance in block production)}

Scope/context: a set of simplex-chains (in the same simplex) that use the same PoW hashing algorithm.

Miners gain revenue in two ways: block rewards and transaction fees.

For a given simplex-chain, the block rewards are essentially fixed block-to-block; i.e., the typical difference in block reward between a block and its parent(s) is negligible.

However, there can be a large difference in the transaction fees of a block compared to those of its parent(s).
This is because transactions are produced (by users) during the gaps between blocks, and a block cannot include transactions that have already been included in prior blocks.
Thus, ``unconfirmed'' transactions (which have not yet been included in a block) accumulate between blocks, typically sorted to prioritize transactions with the highest fees, are ``cleared out'' when a new block is created.
In other words: the transaction fees associated with a block will be somewhat proportional to the gap between that block and its parent(s).

Note, also, that the production of blocks in such chains is stochastic.
Blocks are, \emph{on average}, produced at an approximately constant rate, which is governed by the Difficulty Adjustment Algorithm (DAA).
But, in traditional PoW chains, there is significant variance associated with the production of each \emph{individual} block.

So, in this context, how can block producers (miners) maximize their return on investment (RoI)?

Say that a miner can choose to mine any of $N$ chains (and there is negligible overhead to swapping between them).
The miner should roughly prioritize mining the chain that will produce a block with the largest reward (including transaction fees) divided by that chain's average time between blocks.
Practically speaking, this will often result in the miner choosing the chain with a large number of unconfirmed transactions, and this will often be the chain that has gone the longest without a block having been produced.

Say the set of miners and mining resources (hash-rate) is split between $N$ simplex-chains.
The miner should, on average, mine each chain for the same amount of time; their hash-rate will be, on average, evenly split between all $N$ chains, even though the miner is only mining one chain at a time.

This method works because \emph{all} miners are incentivized to mine the same chain at the same moment.
Thus, all miners are \emph{synchronized} in a decentralized way.

If one chain has a low volume of transactions and/or low transaction fees, then miners might not prioritize mining that chain.
However, this is what the difficulty adjustment algorithm is for!
The difficulty of such a chain will decrease, which increases the reward relative to the amount of work that must be done, which makes that chain competitive again in attracting miners.

Moreover, miners that are not synchronized in this way will reduce their ROI.

Thus, this phenomena is \emph{resonant} --- the synchronization between miners is \emph{stable and attracting}.



\section{Recursive PoR}

% \begin{itemize}
%   \item PoR can be done recursively
%   \item e.g., $\cL \leftrightarrow \cM \leftrightarrow \cR$
%   \item details are a little more complex, but principles the same as PoR
%   \item required for tiling (it might be possible to avoid this, but that's speculative at this point)
% \end{itemize}

% \dots


An essence of PoR is the idea of chain \cL learning that some \cR block was made after some prior \cL block --- that the work attributed to the reflecting \cR block \emph{includes} a reference to part of \cL's history.

Proofs of reflection have (up till now) been direct between the local chain and the reflecting chain.
However, we can use the same technique \emph{recursively} to handle additional contexts.

Consider 3 chains: \cL, \cM, and \cR, that are doing mutual reflection like this:
\begin{equation}
  L \leftrightarrow M \leftrightarrow R
\end{equation}
That is: \cL mutually reflects \cM, and \cM mutually reflects \cR.
Using recursive PoR, \cL can count proofs of reflection via \cR that involve two intermediate \cM blocks.
Since \cL is already doing mutual reflection with \cM, it will already know of PoRs for the relevant \cM blocks, too.
The only missing data is the PoR that the relevant \cM blocks were reflected by an \cR block.
This also means that PoRs are composable into recursive PoRs.

Specifically, we have a situation like this:
\begin{itemize}
  \item \BL{2} has a PoR for \BL{} reflected via \BM{1}
  \item \BL{4} has a PoR for \BL{2} reflected via \BM{3}
  \item \BL{4} has \BM{3}'s PoR for \BM{1} reflected via \BR{2}
\end{itemize}
Thus, \BL{4} implicitly has all the information to deduce the recursive PoR: that \BL{} was imaged by \BM{1}, that \BM{1} was imaged by \BR{2}, that \BR{2} was imaged by \BM{3}, and that \BM{3} was imaged by \BL{4}.

The precise nature of how recursive PoRs should be counted and attributed, as well as which matter and which don't, is explored in the ``Recursive \emph{Proof of Reflection}'' section of the whitepaper.

Recursive PoRs use converted work via the same principles as non-recursive PoRs, though the work may need to be converted in two stages depending on the conversion context used.

Although \cL, \cM, and \cR are doing \emph{mutual} PoR with their neighboring chains, there's no requirement that \emph{recursive} PoR needs to be mutual.
Provided that chains mutually reflect their neighbor, \cL and \cR are free to do one-way recursive PoR via the other.
This is particularly sensible when there is a large asymmetry in the relative work between \cL and \cR: it makes sense for the lighter of the two to use one-way recursive PoR, but the heavier one doesn't gain a substantial benefit by including recursive PoRs via the lighter one.

Recursive PoR is required for \emph{Tiling}.

\section{Simplex Tilings}

When simplexes become part of a simplex tiling they are called \emph{tiles}, or \emph{simplex-tiles}.

\emph{Simplex tilings} (or just \emph{tilings}) are a bidirectional graph of mutually reflecting simplex-tiles.

Simplex tilings require that each simplex-chain in a given simplex-tile does mutual PoR with each other simplex-chain in all adjacent simplex-tiles (this is what is meant when we say that a simplex-tile mutually reflects another simplex-tile).

When each tile in a tiling reflects no more than a certain number of other tiles, we call this number the \emph{valence} ($v$) of the tiling.
We are particularly concerned with tilings of $v > 2$ because it is only these tilings that can grow in an unbounded capacity.
If a tiling has a complex architecture, it could conceivably have a fractional valence (i.e., $v$ is not a whole number).
However, this is unnecessarily complex, so we will only consider tilings with integer valencies.
Thus, we are concerned with tilings of $v \ge 3$.

\subsection{Tree Tilings}

One particular pattern of tiling has been heavily analyzed in the whitepaper: tree tilings.
These are tilings with a root tile, and where each tile has between $0$ and $v-1$ children.

The \emph{core} of a tree tiling refers to the root tile and its immediate children.
The core is the primary source of security in a tree tiling, and over $99\%$ of the tiling's chain-work is done by chains in the core.

Tiles that are \emph{outside} of the core (i.e., grandchildren of the root tile, or tiles further away) use one-way recursive PoR with the root tile to secure themselves.
In general, tiles only require: standard PoRs via all chains in their tile and neighboring tiles, and recursive PoRs via chains in the root tile.

Additionally, all chains should validate PoRs between tiles in the core.
This is a requirement because, provided this is done, the full security of the core is transitive using recursive PoR.
Thus, all tiles outside the core can be roughly as secure as the core, and attacking a chain in any tile requires attacking the core.

Additionally, reflected chain-work in a tiling propagates incredibly quickly.
After a chain in a tile produces a new block (call it \BL{1}), it only takes a single reflecting block of a chain in the parent tile to expose (via recursive PoR) \BL{1} to the next tile on the way to the root tile.
The delay between those two blocks being mined is, on average, the block period divided by the number of chains in the reflecting tile.
So if we have 50 chains in each simplex-tile,\footnote{
  A safe minimum upper-limit of the size of a tile is at least 50 chains under $O(c)$ constraints --- see the whitepaper for the calculations.
} and all chains have a block period of $15$ s, then the per-step delay between \BL{1} being mined a recursive PoR becoming available is $15/50$ seconds.
Additionally, since a recursive PoR is from the local tile to the reflecting tile and back again, the recursive PoR requires $2d-1$ steps, where $d$ is the distance (number of direct links) that are between the local tile and the root tile.
Thus, in this example, reflected work (via one-way recursive PoR with the root tile) begins to become available in $(2d-1) \cdot 15/50$ seconds.
For $d = 9$, this means that a new PoR becomes available to \cL miners around 2.7 seconds after \BL{1} was mined.\footnote{
  Note: this has been experimentally verified via a statistical simulation.
}

In practice, this means that new blocks in a tiling become as secure as the root tile with an almost negligible delay.

\subsection{Other Tiling Patterns}

There are an infinite number of tiling patterns.
Some examples are discussed in the whitepaper and shown in \autoref{sec:patent-figs}.

Not all of these patterns are useful, though.
Additionally, it might be difficult or impossible to secure some patterns.
While a security architecture for tree tilings is presented in the whitepaper, it is not expected that all tilings can be designed in a secure way, and it may take considerable work to show whether any particular tiling pattern is secure or not.

It is questionable whether other tiling patterns are worth looking into further, since tree tilings satisfy the three criteria of Buterin's Trilemma.
Those three criteria are: each chain is $O(c)$ constrained (decentralization), each chain is as secure as the network, and the network is scalable.
Scalability is achieved because the tree structure allows for network capacity to grow exponentially faster than the average distance between tiles (and thus the maximum size of SPV proofs between any two chains in the network does not conflict with increasing capacity via adding new tiles).

\section{Child-chains / Dapp-chains / Sharding}

\mk{This section / claim might not be necessary. It's basically just one-way PoR with a focus on a particular use case, but including it might be more hassle than it's worth.}

Here, a ``child-chain'' is specifically the category of blockchains that are facilitated and secured by a parent-chain in a one-way relationship.\footnote{
  There is no widely agreed upon term for this class of blockchain, so we use \emph{child-chain}.
  Note that some definitions of ``child-chain'' (in other sources) may be incompatible with the definition we use here.
}
For example, techniques like sharding, ``parachains'' (as in the Polkadot network), and dapp-chains are all (typically) types of child-chains.
Crucially: they depend on a parent-chain (e.g., Ethereum's \emph{Beacon chain}, Polkadot's \emph{Relay chain}, etc).
The term ``sidechain'' refers to multiple types of blockchains, some of which are child-chains.\footnote{
  \href{https://www.bitcoin.com/get-started/what-are-sidechains/}{This article (``What are sidechains?'')} covers the two types and provides examples.
}

PoR provides a method for hosting child-chains via one-way PoR (where the child-chain is reflected in the parent-chain).

Ideally, a large asymmetry should exist between the local\footnote{
  \emph{Local} work is the work associated directly with the creation of a block.
  Work contributed via PoR is never local work.
} work securing the parent-chain and the local work (if any\footnote{
  The child-chain can use a consensus mechanism that uses features that are not readily convertible, e.g., Proof of Authority, or avoid the idea of block rewards and/or a native token all together.
}) securing the child-chain --- the parent-chain should have far more local work than the child-chain.
In this way, the parent-chain can secure many child-chains.

One advantage of using PoR for hosting child-chains is that it is incredibly efficient as the burden of recording and validating PoRs is entirely on the child-chain.
In some cases, only the hash of a child-chain block needs to be reflected by the parent (typically 32 bytes).
However, if the entire header of the child-chain is recorded such that a headers-only version of the child-chain is available on the parent-chain, then efficient SPV proofs can be used to facilitate techniques such as cross-chain transactions.
Since child-chain headers can be relatively small ($\sim 80$ bytes), a modest blockchain could host thousands of child-chains using this technique.

Although other systems of child-chains superficially resemble the method of hosting child-chains via PoR, they differ substantially in their implementation and security architecture.
Crucially, those other systems do not involve the conversion of work.

Child-chains via PoR can be combined with simplexes to increase the capacity of a blockchain network.

\section{Proxy chains}

\mk{Note: this is not covered in the WP}

A ``proxy chain'' is a special simplex-chain that a simplex uses (in combination with recursive PoR) to integrate external work done on an otherwise independent blockchain which is not part of the simplex.
It is \emph{via} the \emph{proxy chain} that the security of that external chain is shared with the simplex.

To illustrate this arrangement, let's consider a simplex with 50 chains, where only one of those simplex-chains is a proxy chain.
This proxy chain records all of the valid headers of the external chain and all valid PoRs that can be proven via that header.

Since there are PoRs of the proxy chain reflected in the external chain, there must be some method of the external chain reflecting the proxy chain.
Additionally, we need to be able to prove that there were \emph{zero} blocks reflected by the external chain when that is applicable.\footnote{
  We must be able to do this because we cannot assume that all miners of the external chain will participate and produce blocks (of the external chain) that reflect the proxy chain.
  When an external block without reflections is produced, its weight contributes to the proxy chain's block(s) that were most recently reflected by an ancestor of the external block.
}

When a miner of the external chain produces a block, miners of the proxy chain include the header of that block in their draft blocks, along with a PoR of all reflected blocks.
These PoRs are special in that the rest of the simplex is aware of them, validates them, and integrates work contributed by the external chain via the proxy chain as though the external chain were directly contributing work to the simplex.
This integration is done via recursive PoR.

Some external chains might be capable of reflecting the proxy chain via typical \emph{transactions}.
Such external chains require suitably rich smart contract systems at a minimum.

For external chains that do not have suitably rich smart contract systems, reflections must have a \emph{known location} within the block so that it is possible to prove exactly how many proxy chain blocks were reflected by any particular external block.\footnote{
  For external chains \emph{with} suitably rich smart contract systems, the reflecting smart contract must have a known location in \emph{state}.
  Additionally, reflecting transactions submitted to the smart contract must be reliably included in blocks of the external chain --- i.e., the external network is not so congested as to effectively censor reflections.
  This may be mitigated to some degree via block rewards paid to the miner of the external chain and distributed via the proxy chain.
}
For example, if Bitcoin were used as an external chain, reflections could be provided in the \emph{coinbase} transaction (which is always the first transaction), since this is data with a known location in the Bitcoin block and a suitable reflection scheme will allow the exact number of reflected blocks to be proven (including zero).
However, Bitcoin could not provide reflections of the proxy chain via any other transactions, since proving the number of reflected blocks requires checking every transaction in a given Bitcoin block.

Note that neither permission from the external chain's community nor a soft-fork of the external chain's protocol are required for that external chain to contribute work via the proxy chain.
Provided their is suitable freedom in the external chain's protocol (which there typically is), each individual miner on the external chain can reflect blocks of the proxy chain at their discretion.

Additionally, note that the conversion of work (from that of the external chain to that of the proxy chain) requires a suitable decentralized exchange (DEX) hosted on the proxy chain, and a reliable exchange rate (between root tokens of the proxy chain and root tokens of the external chain) must be readily provable and available to the conversion algorithm.


\subsection{Comparison to Merged Mining}

A major difference between proxy chains and merged mining (aka AuxPoW) is that proxy chains use the canonical history of that other chain, but merged mining does not.

Merged mining is a PoW-specific process whereby miners of a primary chain (e.g., Bitcoin) can simultaneously mine one or more secondary chains (e.g., Namecoin) without reducing their hash-rate on the primary chain.
That is, the PoW solutions that the miner produces could be valid on the primary chain, the secondary chain(s), both, or neither.
Typically, if a PoW solution is found for the primary chain, that solution is also valid for the secondary chain(s).\footnote{
  This is only true when the secondary chain's PoW validation method is the same as the primary chain's.
  If the secondary chain uses a different method to validate the PoW, then solutions for the primary chain are not necessarily solutions for the secondary chain.
}
This is because all hash-rate contributing to a secondary chain is also contributing to the primary chain, but not necessarily vice-versa.

Since some PoW solutions for the secondary chain are not solutions for the primary chain, it is clear that merged mining and proxy chains are distinct methods of sharing PoW between blockchains.
