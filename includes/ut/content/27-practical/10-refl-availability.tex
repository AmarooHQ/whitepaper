\subsubsection{The Availability of Reflected Blocks}

\label{sec:availability-of-blocks}

What happens if a chain reflects a valid block that is not available?
Could an attacker use this to their advantage?

For example, consider the following situation (\autoref{fig:unavailable-ex1}).
\cL and \cR are two mutually reflecting chains, and the most recently produced block is \BL{}, which reflected \BR{}.
Next, a malicious \cR miner produces a valid block (\BR{1a}) which reflects \BL{}.
That miner broadcasts the \emph{header} of \BR{1a} along with a PoR branch proving that \BL{} was reflected, but does not broadcast the rest of the block.
The \cL miners receive the header and PoR branch, and shortly thereafter an \cL miner produces \BL{1}, which reflects \BR{1a}.
Since other (honest) \cR miners cannot build on \BR{1a}, they must work on the draft block \BR{1} instead.
Note that, although \BR{1} will almost certainly reflect \BL{}, whether it reflects \BL{1} is at the miner's discretion.

The attacker can use this situation to their advantage if \BR{1a} has precedence over \BR{1} (i.e., it's favored by the fork-rule).
In that case, the attacker can publish \BR{1a} \emph{after} \BR{1} is mined for an advantage.\footnote{
    This is similar to the \emph{selfish mining} attack published in \citeSelfishMiningFull{}.
    It could also be chained to effect a doublespend.
}
When does this case occur?

If \BR{1} does \emph{not} reflect \BL{1}, then \BR{1} will claim the same chain-weight as \BR{1a}.
However, \BR{1a} is favored over \BR{1} since the PoR via \BL{1} contributes weight to \BR{1a} (as discussed in \autoref{sec:counting-work}).
So the attacker \emph{always} has the advantage if \BR{1} \emph{does not} reflect \BL{1}.

If \BR{1} does reflect \BL{1}, then \BR{1a} is implied as an earlier block, so should have precedence.

Both these situations makes sense: sometimes two \cR blocks will be created near-simultaneously, and occasionally only one of those blocks will be reflected by an \cL block.
In those naturally arising cases, we'd \emph{expect} the reflected block (\BR{1a} in this case) to take precedence.
Either because it was reflected when \BR{1} wasn't, or because, for \BR{1} to reflect \BL{1}, \BR{1a} must have existed first.

So, we seem to have a problem: on the one hand, an attacker could withhold a block (but not the header or PoRs) to gain some advantage; on the other hand, prioritizing the earlier block seems to be necessary and correct behavior when this situation arises naturally.

The only difference between these two situations is whether \BR{1a} is available or not; so this will be our discriminating factor.

Can \cR miners do anything to prevent \cL miners reflecting \BR{1a} before the block body is released?
The \cR miners can't prevent a withheld \cR block from being produced or reflected, but, \cR miners can still influence \cL miners' choice to reflect \BR{1a} (and withheld blocks in general).
\cL miners want their blocks to be reflected by \cR miners so that future \cL blocks will build on top of their's.
So \cR miners could refuse to reflect some \cL blocks --- particularly, \cL blocks that reflect \cR block headers without a known body (such as \BR{1a}).

Since \cL miners face the same problem (withheld but reflected \cL blocks), both \cL and \cR miners are incentivized to cooperate.
This is forms a stable equilibrium provided that the honest miners have excess bandwidth and that the attacker has less than half the combined (post-conversion) hash-rate.

Another way to look at this is that PoR only works when all blocks are available.
This isn't surprising because blockchains generally only work when all (canonical) blocks are available.
Since miners only want to participate in systems that work (how else would they earn income?), they will adopt the practices required to make the system work.

\subsubsubsection{Bandwidth Requirements}

In the case of just two chains, the bandwidth requirements for \cL miners are approximately doubled, but the storage and computational requirements are not.
While there is some storage and computational overhead on the part of reflected \cR blocks, these are close-to-negligible when compared to the mined chains: miners need only to store \emph{recent} \cR blocks and verify that they are \emph{structurally} valid.
While this is technically an $O(c)$ computational load per block (since blocks are $O(c)$ bytes large), practically this load is far smaller than the $O(c)$ load of \emph{fully processing} a block, so we can treat it as a constant overhead ($O(1)$).
Since only recent blocks are stored, the storage requirements are also $O(1)$.

If there are $O(c)$ many chains, then requirements are: $O(c^2)$ for bandwidth, $O(c)$ for storage, and $O(c)$ for computation.
As we will see in \autoref{bandwidth-complexity}, the practical bandwidth requirements are acceptable (on the order of 1 MB/s or so\footnote{
    A rule of thumb: 1 MB/s here corresponds to 1,000-4,000 TPS.
    Also note that this is only a requirement for miners and full nodes \emph{after} a desired chain has been fully synchronized.
}).
Assuming that holds true, we can conclude that the \AxiomOfAvailability{} is not a bottleneck for scalability.

See \autoref{sec:bandwidth-complexity} for a deeper discussion of bandwidth complexity.
