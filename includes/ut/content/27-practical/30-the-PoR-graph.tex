As a simplex ages, a complex graph of PoRs is produced (and it is a DAG).
Each vertex represents a block in some simplex-chain, and the outgoing edges point to reflected blocks.

Since there are $N_1$ chains, and each block has $\sim N_1$ reflections on average, the total number of reflections, per block period, is $\sim {N_1}^2 = O(c^2)$.
Does this present a problem for fully validating nodes that wish to verify the entire PoR graph?

Recall that in \autoref{sec:exploiting-segmented-state}, we took advantage of redundant data within the PoR graph.
Particularly that, provided we knew \emph{which} blocks were reflected and the \emph{ordering} used to create the PoRs root, we could deterministically reconstruct those parts of any simplex-chain block.
However, this relied on either tracking \emph{the entire} PoR graph, or additionally downloading all missing merkle branches corresponding to PoRs used by the reflected block.

Why is so much information required?
The reason is that each miner can choose \emph{whether} to reflect any block (assuming that the block is available), and has the freedom to choose the \emph{position} of each reflected block in the reflections tree.

Regarding the \emph{position} of reflected blocks -- this is easy to solve.
All we need to do is ensure there is only one position that a block can be in.
For example, we could require that reflected blocks are ordered based on the ordering of their genesis blocks (which is fixed).
If two or more blocks from a single simplex chain are reflected, we can use a sub-ordering method (of which there are many options).
This gives us a total ordering, meaning that we only need to know \emph{which} blocks were reflected to reconstruct this segment of a block.
Alternatively, we could use a merklized prefix tree which achieves the same goal.
Either way, we have reduced the required information from a \emph{list} of block hashes to a \emph{set} of them.

It is clear that miners need some freedom to choose \emph{whether} to reflect a block or not.
For one, miners must be able to choose to reflect \emph{new} blocks as they appear.
Additionally, due to the \AxiomOfAvailability, miners must not reflect unavailable blocks, even if a valid PoR can be generated.
However, because all honest miners obey the \AxiomOfAvailability, there is never a reason for an honest miner \emph{not} to reflect a block that is available -- doing so will always increase the overall chain-weight of that miner's draft block.

So, if an honest miner's block, \BL{}, reflects some block, \BR{}, then any block reflected by \BR{} must also be available (since the \AxiomOfAvailability is recursive).
If a block is available then a PoR is possible.
Therefore, an honest miner should reflect all non-local blocks that were reflected by \BR{} but have not already been reflected by an ancestor of \BL{}.

Let's call this a state of \emph{maximal reflection}, and say that such a PoR graph is \emph{maximally reflective}.

\subsubsubsection{Maximally Reflective PoR Graphs}

Specifically, we can say this about any PoR graph in a state of maximal reflection: for every block \BL{}, and for every block \BR{} reflected by \BL{}, then every block $b$ that is reflected by \BR{} satisfies one of: $b$ is reflected by \BL{}; or $b$ was reflected by an ancestor of \BL{}; or $b$ is an ancestor of \BL{}.

Notice that, if \BL reflected any blocks, there will always be at least one block that \emph{was} reflected by \BL that was \emph{not} reflected by any other block that was reflected by \BL.
Let us call these blocks the \emph{tips} of the PoR graph from \BL's perspective.
PoR graph tips might reflect other blocks reflected by \BL, too.

For example, consider this PoR graph segment between 3 chains \cL, \cQ, and \cR:
\begin{equation*}
    \xyMChains{
        \xyL{\text{Chain \cQ}} & \cdots & & & \xBQ{} \arm[lll] \arf[lld] \arf[ldd] & \\
        \xyL{\text{Chain \cL}} & \cdots & \xBL{-1} \arm[l] & & & \xBL{} \arm[lll] \arf[lld] \arf[lu] \\
        \xyL{\text{Chain \cR}} & \cdots & & \xBR{} \arf[lu] \arm[ll] & & \\
        \xyTimeHoriz{rrrrr} &&&&&
    }
\end{equation*}
Here, \BL{} reflects both \BQ{} and \BR{}, and \BQ{} also reflects \BR{}.
Thus, from \BL{}'s perspective, \BQ{} is a \emph{graph tip}; and, from \BQ{}'s perspective, \BR{} is a \emph{graph tip}.

Starting from \BL{-1}, we could completely describe this section like so:
\begin{itemize}[notopsep, noitemsep]
    \item \BR{} reflects \BL{-1}; and
    \item \BQ{} reflects \{{\BR{}, \BL{-1}}\}; and
    \item \BL{} reflects \{{\BQ{}, \BR{}}\}.
\end{itemize}

If the PoR graph is not maximally reflective, then we must specify the complete set of reflections for each block.
However, \emph{when maximally reflective}, most of that information is redundant (about half in this example).

We \emph{do} still need some information for each block, however, we can recreate the full PoR segment with less information -- some of the reflections are \emph{implied} and can be omitted:
\begin{itemize}[notopsep, noitemsep]
    \item the PoR graph segment is maximally reflective; and
    \item \BR{} reflects the tip \BL{-1}; and
    \item \BQ{} reflects the tip \BR{}; and
    \item \BL{} reflects the tip \BQ{}.
\end{itemize}

We can see that the maximally reflective quality has at least two important properties.
Firstly: we have \emph{drastically}\footnote{
    The theoretical overhead is still $O(c)$ per block, but practically we expect the overhead to be a similar size to the header which is $O(1)$.
    It's explained shortly.
} reduced the amount of information needed to completely describe the graph segment: $O(c^2) \to \sim O(c)$ -- an example is shown in \autoref{fig:por-graph-tips}.
Secondly: the PoR graph, according to each chain, \emph{converges} into a single, consistent PoR graph.
In essence, any block in a maximally reflective PoR graph shares a \emph{common history} with all prior blocks in the graph.

        This demonstrates how maximally reflective PoR graph segments with $O(c)$ many chains can be described using $\sim O(c)$ information.
        Thick dotted arrows represent reflections of PoR graph \emph{tips}, and semitransparent arrows show other reflections -- these reflections and implied via the reflection of the graph tips.
        This also shows that the DAG of tip-reflections is the \emph{longest} path of reflections between two blocks.
    }
    \label{fig:por-graph-tips}

Is there an intuitive explanation for the reduction in complexity of the PoR graph?
Yes.
To start with, let us assume that there is no \emph{propagation delay} -- i.e., all miners instantly receive, validate, and incorporate all blocks into the PoR graphs of their draft blocks.
In this case, no blocks are every mined simultaneously, and so each block will reflect exactly one PoR graph tip.
Since there are $O(c)$ many chains, and we need to add $O(1)$ extra information per header (the reflected tip), this is $O(c)$ extra information all up.

In practice, blocks \emph{will} sometimes be mined simultaneously.
So, even if \emph{most} of the time a block only reflects one tip, \emph{some} of the time that block will reflect multiple tips.
The frequency of simultaneous blocks is dependent on the number of chains ($N_1$), the block frequency of each chain ($B_f$), and some propagation delay ($\phi$ seconds).
Two blocks are simultaneous if they are mined within $\phi$ seconds of each other
In the $\phi$ seconds before that most recent tip was mined, we expect that $\sim N_1 B_f \phi$ other tips were mined (from any simplex-chain).
Unless a block contains no reflections, it must reflect at least one graph tip (which happens with probability $1 - {N_1}^{-1}$).
So, we expect each block to reflect $1 + N_1 B_f \phi$ tips.
For $N_1 = 100, B_f = \nicefrac{1}{15}, \phi = 0.3$, we expect
each block to be simultaneous with $\sim 2$ others, and each block to reflect 3 graph tips on average.

Therefore, the overhead to reconstruct the PoR graph -- and every PoR segment of every simplex-chain block -- is, on average, $g (1 + N_1 B_f \phi)$ bytes per block, where $g$ is the length of a hash.
As $g$, $1$, $B_f$, and $\phi$ are constants, the overhead thus has complexity $O(c)$ \emph{per block-period per simplex-chain}.
Since we're tracking $O(c)$ chains, the overall load is $O(c^2)$.

The total bandwidth required to track the PoR graph (excluding verifying the availability of blocks) is: the overhead per block, plus the block header, all multiplied by the network-wide blocks per second rate.
Thus, the total bandwidth is $N_1 B_f (B_h + g(1 + N_1 B_f \phi))$ B/s -- which is $O(c^2)$.

However, we estimated before that we should expect to require just 3 graph tips on average per block (which seems quite low).
Practically speaking, the overhead is only significant when the header size is much smaller than the overhead: $B_h \ll g (1 + N_1 B_f \phi)$.
If we plug in our rough numbers from before, we find $g (1 + N_1 B_f \phi) \approx 100 \approx B_h = O(1)$.

There \emph{is} a practical limit (depending on $B_f \phi$) for how large $N_1$ can grow before this overhead is non-negligible.
\emph{However}, if we capped the expected overhead to, say, 256 bytes -- $g(1+N_1B_f\phi) \le 256$ -- then we find $N_1 \le 7(B_f \phi)^{-1} \approx 350$.
Capping the overhead to 128 bytes yields $N_1 \lesssim 150$.
Note that maximal values of $N_1$ are inversely proportional to $B_f$, so modifying $B_f$ doesn't change the expected overhead.

\subsubsubsection{Optimization or Contradiction?}

We calculated the overhead to be $g(1+N_1 B_f \phi) = O(c)$ -- this is because we assumed that $O(B_f \phi) = O(1)$.
However, if this were really the case, we should be able to optimize the PoR sections of blocks (similar to \autoref{sec:exploiting-segmented-state}).

We could try to design the protocol like this: \emph{instead of recording all reflections, each block records only the minimum necessary to reconstruct the PoR graph}.
This would increase the overall bandwidth required to track the PoR graph, but our expression remains the same: $N_1 B_f (B_h + g(1 + N_1 B_f \phi))$.

Since the overhead is $O(c)$, and recording all reflections is also $O(c)$, can we swap in this new process to increase scalability?

The old PoR sub-block takes up $N_1 B_f \alpha$ B/s of capacity (where $\alpha$ represents the bytes per reflected simplex chain and $\alpha \in [16, 512]$).

The new PoR sub-block instead takes up $B_f g(1 + N_1 B_f \phi)$ B/s of capacity -- we exclude the block's header since that's already part of the block.
If $k_{1,B}$ B/s of a chain's capacity is dedicated to reflections, then we have:
\begin{align}
    k_{1,B} &= B_f g(1 + N_1 B_f \phi) \nonumber \\
    N_1 &= \frac{1}{B_f \phi} \Big(\frac{k_{1,B}}{B_f g} - 1\Big)
    % & \text{Note that $N_1 \propto \phi^{-1}$}
    \label{eq:bad-n1-with-phi}
\end{align}
Plugging in our numbers from before (excluding $N_1$), yields $N_1 \approx 23 (k_{1,B} - 2.1)$.
If $k_{1,B}$ = 1,500 B/s, then $N_1 \approx$ 34,500.

Of course, 34 thousand chains is a lot, and tracking the PoR graph completely would require $\sim 52$ MB/s of bandwidth and require more than 1 PB per year to store this data.
Each block would reflect, on average, 34k other blocks.
Every block period, keeping up with the PoR graph would require calculating 34k PoRs roots -- although there are significant optimizations to avoid recalculating these from scratch.

\aside{I don't know about you, but I'm getting the suspicion that this isn't really an $O(c)$ load.}

One of our premises before was that $O(N_1 B_f \phi) = O(c)$, but is that really the case?
Certainly $O(N_1) = O(c)$, and $O(B_f) = O(1)$, but does $O(\phi) = O(1)$?

There is a good reason to think $O(\phi) = O(1)$.
At some point, propagation delay is limited by the speed of light.
So latency must have a definite minimum, which is a constant.

However, the physical limits on latency do not dominated real-world latency yet.
Near-future networking technologies, like LEO satellite constellations, will reduce latencies over significant distances.
Moreover, even as the best-case minimum latency approaches physical limits, technology will continue to improve latency in \emph{bandwidth intensive} contexts.\footnote{
    This is something we didn't consider when estimating $N_1$ in \autoref{eq:bad-n1-with-phi} -- that the propagation delay will increase as the excess capacity of nodes' available bandwidth decreases.
    Like all systems, response time is inversely proportional to excess capacity.
}
Therefore, $O(\phi)$ \emph{should not} be considered $O(1)$, but rather should be considered $O(c^{-1})$: as technology improves, $\phi$ decreases.

If $O(\phi) = O(c^{-1})$, this resolves the contradiction.
% First, recall $N_1 \propto \phi^{-1}$ from \autoref{eq:bad-n1-with-phi}.
% This is a contradiction if $\phi$ is $O(1)$, but makes sense if $\phi$ is $O(c^{-1})$.
It means that $O(N_1 B_f \phi) = O(1)$.
That matches our intuition from earlier, \emph{and} means that maximally reflective PoR graphs really are only $O(c)$ complex, rather than $O(c^2)$.

We can also explain why we had such a large $N_1$ estimate before -- we took an $O(1)$ load and blew it up to an $O(c)$ load.
So we effectively changed $O(N_1)$ from $O(c) \to O(c^2)$.
That meant that network-wide bandwidth and storage requirements went from $O(c^2) \to O(c^3)$.

Curiously, we can still \emph{in principle} use this optimization idea to increase network throughput in the future, if we want to.
In practice, the effects would be similar to increasing the PoRs sub-block size.
However, this is best left as \emph{excess capacity} in \UT{}'s architecture -- a resource to tap into if we get desperate, but not something that we should plan to use.

\subsubsubsection{The Longest PoR Chain}

\autoref{fig:por-graph-tips} shows us an interesting feature of maximally reflective PoR graphs: between two given blocks, the union of the paths via PoR graph tips both \emph{visit every block} and are the \emph{longest} paths between any two blocks.
This is somewhat self-evident: since the PoR graph is a DAG, there is no way to return to a block once we have visited a it.
Thus, if a path exists that visits every block, then it must be a longest path because there are no unvisited blocks.
A longer path would need to visit more blocks, but there are no more blocks, therefore no longer path exists.
