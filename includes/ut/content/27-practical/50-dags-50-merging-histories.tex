\subsubsection{Merging Histories}

\label{sec:merging-histories}

% some commands to draw boxes around groups of blocks
\def\blkGrp#1{\save [].[r]!C="g#1"*[F.]\frm{}\restore}%
\def\blkGrpM[#1]#2{\save [].[#1]!C="g#2"*[F.]\frm{}\restore}%

If a block \BB{2} has two valid parents, how can we resolve this into one consistent history?

Consider the following subgraph, where squiggly arrows indicate secondary parents: \autoref{fig:merging-hist-sg-1}.

\begin{figure}
    \centering
    \begin{equation*}
        \xyMChains{
            & & & \xBB{1a} \arm[ld] & & \xBB{2a} \arm[ll] \\
            & \cdots & \xBBi \arm[l] & & \xBB{1b} \arm[ll] & & \xBB3 \arm[lu] \ars[ll] & \cdots \ar[l] \\
            & \xyTimeHoriz{rrrrrr} &&&&&&
        }
    \end{equation*}
    \caption[A simple block subgraph.]{A simple block subgraph. Standard arrows indicate primary parents, and squiggly arrows indicate secondary parents.}
    \label{fig:merging-hist-sg-1}
\end{figure}

By the ordering algorithm we covered above, we know that the blocks will executed in this order: \BBi, \BB{1a}, \BB{2a}, \BB{1b}, \BB{3}.

Typically, a blockchain's state transition function can (at least partially) be verified via the pattern in \autoref{alg:state-trans-simple}.
We first load the parent's state, apply each transaction in sequence, and then calculate the new state root.
If this matches the state root recorded in the block header, then the state transition is valid (all else being equal).
This works fine for some blocks that have only one parent (e.g., \BB{1a}, \BB{2a}).

\begin{algorithm}
    \caption{A basic state transition verification function}
    \label{alg:state-trans-simple}

    \begin{algorithmic}
        \Procedure{VerifyStateTransition}{parentStateRoot, TXs, stateRoot}
            \State midState $\gets$ \Call{LoadStateFromRoot}{parentStateRoot}
            \For{tx in TXs}
                \State midState $\gets$ \Call{ApplyTx}{midState, tx}
            \EndFor
            \State \Return{stateRoot $==$ \Call{GetRoot}{midState}}
        \EndProcedure
    \end{algorithmic}
\end{algorithm}

We \emph{can} use this algorithm \emph{from \BB{1b}'s perspective} to ensure \BB{1b} is internally consistent;
however, we \emph{cannot} use it with the above subgraph.

Why?
Because \BB{1b}'s parent is \BBi, but the block immediately executed prior to \BB{1b} was \BB{2a}.
Thus, the algorithm doesn't work for \BB{1b}: we need to use a different prior state, and therefore the \emph{resulting} state root \emph{will not match} the state root in \BB{1b}'s header.

Moreover, the algorithm doesn't exactly work for \BB{3}, either.
In \BB{3}'s case, its primary parent is \BB{2a}, but it's state root should be the result of applying \BB{1b}'s transactions to \BB{2a}'s output state, and then applying \BB{3}'s transactions to that mid-state.

It is clear that the algorithm breaks for \BB{3} because it has more than one parent.

The reason that it breaks for \BB{1b} is more subtle: \BB{1b} is not part of the \emph{main chain}.

Observe that the pattern works for on-main blocks with a single parent, but not for off-main blocks, nor for on-main blocks with multiple parents.

The solution is to combine new off-main ancestors (\BB{1b}) with the relevant on-main descendant (\BB{3}) and process them as a single operation.
In principle, we're collapsing the full block-DAG down to just the main chain, so that traditional blockchains' state-transition logic works for block-DAGs, too.

This has two important and related implications.
First: transactions in off-main blocks may not be valid at execution time, because the previous state root changes.
Second: only the state roots of on-main blocks are accurate and reliable.
We should be careful to verify proofs against \emph{only} on-main blocks --- methods like SPV \emph{are not safe} against off-main blocks.

We can now describe the execution in terms of the main chain by grouping novel off-main ancestors with the next main chain block:
\begin{equation*}
    \xyMChains{
        & \cdots \arm[r]
            & \xBBi \arm[r]
            & \xBB{1a} \arm[r]
            & \xBB{2a} \arm[r]
            & \xyBDraft{\BB{1b}} \arm[r] \blkGrp1
            & \xBB3 \ar[r]
            & \cdots \\
        & \xyLabelHoriz{Execution Order}{0pt}{rrrrrr}{r30pt} &&&&&&
    }
\end{equation*}
The dotted boundary around (\BB{1b} $\to$ \BB{3}) indicates that the blocks are processed as a group.
The dashed boundary around \BB{1b} indicates that it is, in a sense, \emph{virtual} within the state-transition function.
\BB{1b} is more like a part of \BB{3} than a block in its own right.

See \autoref{fig:merging-hist-sg-4} for an addition example.

\pz{In the following paragraph, why \BB{1b}?}
If we want to support stateless full nodes (and fraud proofs), this grouping strategy adds a constraint to the block structure.
Particularly, the complete witness structure of \BB{3} is not simply the witnesses for \BB{3}'s transactions combined with the witnesses for \BB{1b}'s.
Instead, it is a new witness structure initialized from \BB{2a}'s state, and must cover \emph{both} blocks' transactions.

In regards to fraud proofs, the technique that we discussed in \autoref{sec:stateless-and-fraud-proofs} requires additional data to be included in \BB{3}.
Recall that the transaction root should correspond to a merkle tree with leaves alternating between state roots and transactions, with each root being that of the state immediately prior to the transaction's execution.
Thus, \BB{3} must provide intermediate state roots that uniquely correspond to each transaction in each novel off-main ancestor.
Furthermore, the transaction root should commit to \emph{all} of these \{mid-state root, transaction\} pairs, not only those of transactions that were included directly in \BB{3}.
